# OSGate 1.0.0

OSGate — SOCKS5-шлюз, который открывает целевые TCP-соединения **исключительно через SSH `direct-tcpip`**. Требуется Python 3.12+, стандартный OpenSSH Server на удалённом узле (`AllowTcpForwarding yes`). Не требуется `ssh -D` и не используется локальный интернет вместо SSH. Поддерживаются IPv4, IPv6, домены с удалённым DNS, клиентская авторизация RFC1929, постоянные SSH-транспорты, несколько серверов, переключение **новых** TCP-соединений, SQLite, русскоязычная веб-панель и Telegram-оповещения. Версия **1.0.0** прошла базовые интеграционные проверки на реальном OpenSSH-сервере `park`. Указанные ниже ограничения и сетевые рекомендации сохраняют силу.

## Как работает

`Приложение → SOCKS5:1080 (авторизация) → OSGate → AsyncSSH transport → SSH direct-tcpip → нужный хост:порт`.

При потере соединения действующие TCP-сеансы завершаются. Новые используют резервный маршрут. При отсутствии исправного SSH возвращается ошибка SOCKS5, **никакого прямого подключения**. `socks5h://` передаёт домен на прокси, тогда как `socks5://` в curl может разрешить домен локально.

## Установка одной командой (новая Linux-машина)

```bash
curl -fsSL https://raw.githubusercontent.com/ogsvnv/osgate/main/bootstrap.sh | bash
```

Bootstrap загружает официальный репозиторий в `~/osgate` и запускает интерактивный
мастер с выбором Docker Compose/systemd. **Для ввода паролей необходим интерактивный
терминал**; мастер читает ввод из `/dev/tty`, а не из канала curl.

Можно сразу выбрать Docker: `curl -fsSL https://raw.githubusercontent.com/ogsvnv/osgate/main/bootstrap.sh | bash -s -- --mode docker`.
Параметры: `--mode docker|systemd`, `--dir /absolute/path`, `--check`, `--update`.
Поскольку команда загружает и выполняет код из сети, её следует использовать только
из доверенного официального репозитория. Для проверки исходников сначала скачайте
`bootstrap.sh` в файл и изучите его, затем выполните через `bash`.

## Мастер установки (рекомендуется)

Для Ubuntu/Debian доступен интерактивный установщик с выбором Docker Compose или systemd,
проверкой зависимостей, настройкой портов, SSH-ключей и созданием администратора:

```bash
git clone https://github.com/ogsvnv/osgate.git && cd osgate
sudo ./install.sh
```

Просмотр состояния: `sudo ./install.sh --check --mode docker` или
`sudo ./install.sh --check --mode systemd`.
Обновление с сохранением настроек и резервной копией SQLite:
`sudo ./install.sh --update --mode docker` (или `systemd`).
Подробно: [docs/installer.md](docs/installer.md). Порты по умолчанию доступны только локально.

## Выбор сетевого доступа к SOCKS5

При установке мастер предлагает **три режима SOCKS5**:

| Режим | Значение | Кто может подключаться |
| --- | --- | --- |
| Только локально (по умолчанию) | `127.0.0.1:1080` | Приложения на самом сервере |
| Со всех интерфейсов | `0.0.0.0:1080` | Устройства из сетей, которым разрешён доступ |
| Конкретный IPv4-интерфейс | Например, `192.168.1.10:1080` | Через выбранный адрес сервера |

**Веб-панель сохраняет локальный доступ `127.0.0.1:5812` во всех трёх режимах.**
Публикация SOCKS5 на всех интерфейсах требует отдельного подтверждения;
у SOCKS5-клиентов обязательно должны быть настроены логин и пароль. Установщик
не изменяет firewall. Для Docker следует учитывать, что публикация портов через
Docker NAT может обходить обычные правила UFW: для ограничения доверенных IP
используйте подходящие правила firewall с учётом Docker (например, цепочку
`DOCKER-USER`) или настройки облачного firewall.

Выбор можно **изменить без переустановки**:

```bash
cd ~/osgate
sudo ./install.sh --access --mode docker
# или для systemd:
sudo ./install.sh --access --mode systemd
```

Эта команда сохраняет `.env`/окружение службы, SSH-ключи, администраторов
и базу данных. Меняется только адрес прослушивания SOCKS5, после подтверждения
пересоздаётся контейнер или перезапускается служба. Файл настроек
сохраняется в `backups/` перед изменением. Также поддерживается
`bootstrap.sh | bash -s -- --access --mode docker` из доверенного официального
репозитория.

## Docker Compose

1. `git clone https://github.com/ogsvnv/osgate.git && cd osgate`
2. `cp .env.example .env && sed -i "s|SESSION_SECRET=.*|SESSION_SECRET=$(openssl rand -hex 32)|" .env`
3. `mkdir -p data ssh && sudo chown 10001:10001 data` (если хостовые файловые права требуют).
4. Разместить отдельный SSH-ключ в `ssh/id_ed25519` и проверить его права; файл `ssh/known_hosts` должен содержать **проверенный вручную** fingerprint удалённого сервера. Не допускается `known_hosts=None`. Для добавления hosts можно собрать ключ `ssh-keyscan -H server.example >> ssh/known_hosts`, **сверив fingerprint через доверенный канал** перед доверием ключу. Каталог `ssh/` не публиковать в Git.
5. `docker compose build`.
6. `docker compose run --rm --entrypoint osgate osgate admin create admin` — интерактивно введите пароль ≥12 символов.
7. `docker compose up -d`.
8. `http://127.0.0.1:5812` — панель администратора. Внесите SSH-сервер с ключом `/ssh/id_ed25519` и `/ssh/known_hosts`. Сервер сохраняется только при успешном SSH и TCP forwarding probe (настраивается HEALTH_TEST_HOST:PORT).
9. Добавьте клиента SOCKS5 на странице «Клиенты».
10. Проверьте:

```bash
curl --proxy socks5h://127.0.0.1:1080 --proxy-user 'user:password' https://api.ipify.org
```

Внешний IP должен совпадать с IP удалённого SSH-хоста. Для доступа к SOCKS5 с других компьютеров настройте привязку портов в Compose и firewall **только для доверенных IP**. По умолчанию оба порта опубликованы на localhost.

В контейнере веб-слушатель работает на `0.0.0.0:5812`, но проброс на хост ограничен `127.0.0.1`. Docker bridge передаёт запросы с IP шлюза (обычно `172.16.0.0/12`), поэтому Compose явно задаёт `WEB_ALLOWED_CIDRS` для loopback и стандартного диапазона Docker bridge. Для более строгой конфигурации задайте в `.env` `DOCKER_WEB_ALLOWED_CIDRS=127.0.0.1/32,::1/128,<адрес_Docker_gateway>/32`, проверив IP gateway своей Docker-сети. Доступ из других контейнеров той же сети контролируйте отдельно. Не открывайте административный порт наружу без HTTPS, авторизации и точных сетевых ограничений. При настройке HTTPS reverse proxy установите `WEB_SECURE_COOKIES=true` и настройте доверенные IP/CIDR, учитывая IP reverse proxy.

## systemd (без Docker)

Перед установкой убедитесь, что есть Python 3.12+ и поддержка `venv`: `python3 -m venv /tmp/osgate-venv-check && rm -rf /tmp/osgate-venv-check`. На Debian/Ubuntu при сообщении об отсутствующем `ensurepip` установите через администратора `python3-venv` (или `python3.12-venv`). Установщик проверяет это заранее и ничего не изменяет при отсутствии пакета. Скопируйте проект в `/opt/osgate`, запустите `sudo bash deploy/install.sh`. Отредактируйте `/etc/osgate/osgate.env`, создайте SSH-ключи в `/etc/osgate/ssh`, создайте администратора с окружением из systemd (см. вывод установщика) и запустите `sudo systemctl enable --now osgate`. Для CLI при systemd используйте `EnvironmentFile`, не размещайте секреты в shell history. Установщик **не меняет firewall**. Для UFW разрешайте только нужные адреса: `sudo ufw allow from <CLIENT_IP> to any port 1080 proto tcp`; админ-порт 5812 оставляйте на loopback. Проверяйте сохранение доступа к SSH до правок firewall.

### CLI

`osgate start`, `osgate version`, `osgate check`, `osgate status`, `osgate config validate`, `osgate admin create admin`, `osgate admin reset-password admin`, `osgate server list`, `osgate server add --name ... --host ... --username ... --key-file /ssh/id_ed25519 --known-hosts-file /ssh/known_hosts`, `osgate server check ID`, `osgate client list`, `osgate client add username`. Прямое изменение серверов через CLI требует перезапуска сервиса, web CRUD — нет.

### Переключение серверов

В панели выберите `failover`, `round_robin`, `weighted_round_robin`, `manual` или `sticky`. В режиме failover есть настройка авто-возврата и его задержки. Заданные приоритеты используются в режиме failover. Для закреплённого клиента можно запретить переключение либо разрешить резерв. Состояния ONLINE/DEGRADED/OFFLINE отслеживаются независимыми асинхронными задачами. Если внешний адрес проверки из `HEALTH_TEST_HOST:PORT` блокируется на SSH-хосте, выберите доступный TCP endpoint через `.env`.

### Подтверждение ключа удалённого SSH-сервера

Ошибка `HostKeyNotVerifiable` означает, что подлинность удалённого SSH-сервера
не подтверждена. В разделе **SSH-серверы → Проверить и подтвердить ключ
SSH-сервера** OSGate показывает **непроверенный** SHA256-отпечаток сервера.
Администратор обязан **сверить его через независимый доверенный канал**:
например, на консоли сервера командой
`ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`.
Затем вручную ввести точно такой же отпечаток и подтвердить доверие.

Новый SSH-сервер можно добавить аналогично: кнопка
**«Показать SHA256-отпечаток»** показывает предъявленный ключ,
после независимой проверки введите его отпечаток в поле подтверждения.

OSGate сохраняет подтверждённые host keys отдельно от приватных SSH-ключей
в `SSH_HOSTKEYS_DIRECTORY` (по умолчанию `/data/ssh-hostkeys` для Docker).
Каталог `/ssh` остаётся только для чтения, исходный `known_hosts`
не изменяется. Если отпечаток не совпал, приложение отклоняет изменение.
**Не подтверждайте ключ только потому, что его показала веб-панель.**
Инструкция: [docs/hostkey-trust.md](docs/hostkey-trust.md).

### Установка SSH-ключа через OSGate

Если при проверке SSH-сервера появляется `PermissionDenied`, откройте
**SSH-серверы → Настроить SSH-доступ**. OSGate попросит одноразовый
пароль удалённого SSH-пользователя и добавит публичный ключ в его
`~/.ssh/authorized_keys` с сохранением уже существующих записей.
Вводимый пароль не сохраняется; fingerprint обязательно проверяется
по заранее известному `known_hosts`. Веб-панель требует авторизации
администратора и CSRF-токен.

Для нового сервера есть галочка «Настроить SSH-доступ через пароль
при добавлении». Если удалённый сервер запрещает парольный SSH-вход,
этот способ недоступен — авторизуйте ключ через уже доверенный
административный доступ. **Не отключайте проверку host key и не
включайте парольный вход исключительно ради установки OSGate.**
Пошаговая инструкция: [docs/ssh-onboarding.md](docs/ssh-onboarding.md).

### Telegram

В `.env` задайте `TELEGRAM_ENABLED=true`, `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`. Отправка не блокирует сетевую обработку; события подавляются при повторе в течение 60 секунд. Не размещайте токены в открытом репозитории.

### Диагностика

`docker compose ps`, `docker compose logs --tail=100`, `osgate check`, веб-панель «Журнал». Команда `curl` с `socks5h://` исключает локальный DNS. Убедитесь, что `AllowTcpForwarding yes` разрешён для нужного пользователя OpenSSH, а сервер видит интернет и известен `known_hosts`.

### Обновление / резервное копирование

Остановите контейнер, сделайте резервную копию `.env`, `data/osgate.db` (или SQLite online backup при работающем приложении) и приватных ключей, обновите исходники, пересоберите образ, выполните `docker compose up -d`. Миграции Alembic применяются на старте. Для восстановления верните persistent data, `.env` и SSH файлы, затем запустите контейнер. Для удаления: `docker compose down`, после безопасного бэкапа удалите каталог только вручную, чтобы не потерять данные.

### Возможности и ограничения версии 1.0

- Реализован SOCKS5 CONNECT/TCP. SOCKS BIND, UDP ASSOCIATE не поддерживаются (возвращается `0x07`).
- Серверы и клиенты редактируются через веб-панель; доступны проверка SSH перед сохранением, ручное переподключение, назначение основного сервера, смена/генерация паролей, изменение лимитов.\n- История **агрегированного** трафика и график соединений сохраняются в SQLite с ограниченным сроком хранения. Посещённые домены в постоянную историю по умолчанию не записываются.\n- Настройки health/reconnect/лимитов доступны без перезапуска в разделе «Настройки работы», но IP, порты и SSH-ключи задаются отдельно через файловую конфигурацию.\n- Опциональная проверка DNS на удалённом сервере: `HEALTH_DNS_ENABLED=true` и `HEALTH_DNS_TEST_HOST=example.com`; проверка выполняется через SSH, не через локальный DNS.
- Нет автоматического развертывания SSH-ключей или UI подтверждения fingerprint; доверие задаётся через отдельный защищённый файл known_hosts.
- Зашифрованные приватные SSH-ключи без агента не поддерживаются в текущей alpha (требуется отдельная схема защищённого passphrase secret).
- Проведена параллельная проверка 20 HTTPS-запросов через `park` (20/20 успешно). Производительность при иных нагрузках не заявляется.
- Базовый E2E с реальным OpenSSH на `park` выполнен (egress IP, fail-closed, client-side разрыв и reconnect). Интеграционные тесты `tests/integration/` требуют явных переменных `OSGATE_E2E_*`.\n- Испытания двух физических SSH-серверов и массовой нагрузки не входят в критерии текущего релиза по согласованному исключению.\n- Внешний TLS обеспечивается обратным прокси; встроенного публичного HTTPS-сервера нет.

См. `tests/`, `CHANGELOG.md`, `docs/release-1.0-checklist.md` и GitHub Actions. Не открывайте публично SOCKS5 и административную панель без проверки сетевых ограничений, HTTPS и собственной инфраструктуры.
